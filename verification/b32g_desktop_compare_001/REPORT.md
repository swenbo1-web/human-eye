# 当前桌面版与 032 + Hook 修复候选同宿主对照

D48 密集任务取得明确整窗收益。六对首次业务均更快，完整 MCP 窗口配对中位少 3.118 秒（37.47%）。G60 首次业务也六对更快，较长的 MCP 启动消化了大半收益，完整窗近乎持平。轻 Hook 已恢复跳过审计，耗时小幅增加。真实空间 Hook 六对均变慢，配对中位增加 58.7 ms（5.21%）。

## 版本和环境

A 是当前桌面实际注册的 `9.7.2+20261110.scale.opt.r1`（137 个运行源）。B 是 `9.7.2+b32hook1`（143 个运行源），对应已推送的 `31792523ecb48a500b8eed0ecb531c7ecc8e767e`，其 BVH 源与 032 集成提交 `6c93f2375d1073b33e721a168f1fcf610ac6dbdc` 字节相同。A/B 安装文件均与各自原安装逐件核验。A 实验启动器与桌面启动器同字节，B 实验启动器只重绑定桌面的同一个 Python 及对应管理器摘要。两臂实际执行完全相同的 Python 3.12.14、NumPy 2.3.5、Pillow 12.3.0 及 `-I -B` 进程标志。[安装和依赖](BUILD_BINDING.json) · [测试合同](PROTOCOL.md)

G60/D12 和 D48 各一次启动隔离 Blender，每个场景的 A/B 所有观测在同一 Blender 进程内串行交错。G60/D12 持有 12 对象、720 三角，D48 持有 48 对象、2,880 三角。固定入口及现场条件各六对，冷指新 Hook 或 MCP 进程，暖指同一 MCP 进程的两次重复读取。表中 A/B 为两臂各自中位，百分比和绝对差取每对变化的中位，胜场只计 B 严格更快。

## 结论

对于 D48 这类计算密集的首次全场近邻任务，候选在更长的启动和更大的证据包之外，仍净省约 3.12 秒。短 G60 首查的几何阶段明显改善，实际完整窗口近乎持平。结果缓存命中、轻量 Hook 和空间 Hook 路径在本批没有提速证据，空间 Hook 的约 59 ms 回退六对一致。轻量 Hook 的可证改进为恢复了完整跳过审计和 trace。结果支持这两份实际场景和此次比较的产品路径，供应商模型与用户完整会话耗时未参与。

试验前后桌面注册、连接器、状态和审计文件的摘要一致，原始发行和隔离安装逐件复核保持。候选未部署到桌面。[保护核验](PROTECTION.json)

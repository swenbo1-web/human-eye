## 为什么局部移动仍接近冷算

全部五序列都只有 `Obj_008` 姿态变化，24 个 resource id/revision、其他姿态、incarnation 和 document epoch 不变。EDIT 的 114 对中，有 **104 对不涉及它，并且在 cold 已经计算过**。

ReadContext 的 generation 含整场 revision，改变后清进度；旧 measurement store 实际仍在，但 mesh 快键包含整个 capture/selection，导致所有新版本对象对失去命中。宿主资源复用已经生效，重复工作集中在服务端几何核。

这 104 对占 EDIT 的 679260/716565 work units、170/184 棵树。它们定位了可消除计算，不是未经测量的时间收益百分比。全目录 packet 验证中位约 0.78 ms，当前远小于重复求解，下一轮不围绕这项小开销扩建框架。

## 保留的问题与判断

- **传输等待期限尚未完全闭合。** 独立假时钟探针确认 MCP 的 100 ms 父期限仍可能获得 30 s 连接等待；Process 写入耗时未扣掉后续相对等待。迟到成功会被拒绝；实际阻塞 socket/pipe 的故障延迟未测。属于已继承的失败返回/取消时延缺口，不能写成严格端到端期限已验收。
- **隐藏来源异常可能损失覆盖。** raw bbox getter 异常会令源 unsupported，而 evaluated bbox 同类异常可保留未知界继续测；evaluated_get 某些异常会产生 unknown 或请求失败。独立 API double 复现分支，未证明真实资产发生，也未发现 false complete。
- **旧 nearest g06 仍失败。** 作者在旧 137 源基线复现相同 partial/complete 期望差异，原期望和日志保留。本轮未独立重跑，不将它掺进 189 通过或宣称修好。
- **原验收脚本的缺口不能因补验而说已修。** 作者原 verifier 缺公开最短距离直接对 oracle、旧资格承诺和完整缺行分母；作者补验及本轮独立复算覆盖了当前结果有效性。下一轮新测量脚本应补这些点，旧文件不改写。

本轮 host 探针初次 harness 缺 math、成本文本对应检查初次遇 CRLF/LF 差异，均按实际工具问题记录，修正后重跑；不算产品失败，也不删除原说明。作者被自动审批拒绝的 pyc 删除不再尝试，未进入 Git。

这些保留项不阻塞正常隔离缓存优化，也不等于完整产品验收通过。后续需要单独选择真实影响最大的能力或故障处理缺口。

# Image incurred-cost correction

Only the new candidate bridge changes; the sealed consumption_run_001 is untouched.
`Budget.image_output` records known generated blocks before checking deadline,
halt or the image quota. The existing Windows ledger lock has a bounded two-second
record-only wait for this accounting and halt persistence; it does not admit a
late tool, publish data, renew an answer deadline or clear a halt.

Attempt-directory creation and final attempt persistence follow the incurred-cost
update. A later qualification/read/decode/reservation failure cannot refund the
known generated-block count. `register_images` still raises the original admission
or processing failure and records no delivery reservation on the refusal paths.
Bridge main therefore retains generated response bytes but publishes no late RX.
Ledger counts are observed constructed blocks, reservations are potential delivery,
and actual model receipt remains unverified. No renderer or global image monitor
was added; unobserved Python rendering is not inferred.

Six directed stdlib checks are prepared in tests_images.py: late known block,
halted blocks accumulating past one without refund, ordinary qualification failure,
and a late fake HE block retained as generated bytes but never published, plus
normal native EOF and a fake HE close exception preserving truthful process receipts. Blocks
are non-PNG placeholders; fake HE streams are memory-only. The checks do not import
the neutral helper or product, decode an image, open sockets, create a real child,
start Blender or call a model. The parent runs exact candidate/test bytes and saves
raw output; this sub-agent performed syntax inspection only, not test execution.

At the parent's request, bridge main also persists STARTED.json and EXIT.json
with its own PID/kind and local timestamps. HE_CHILD_STARTED/EXIT records expose
only the subprocess it owns. HE.close returns bounded wait/kill/wait evidence;
exceptions and unknown/reaped status remain separate from normal bridge EOF.
The final EXIT is written even when the protocol or backend close fails. These
receipts do not assert containment or termination of arbitrary processes a full
Python consumer might create; the parent decides whether known process recovery
is confirmed and whether to stop the remaining planned slots.

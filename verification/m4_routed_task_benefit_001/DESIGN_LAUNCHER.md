# Routed task launcher design

The new entry runs the preregistered serial order N1, P1, P2, N2, N3, P3. Each slot owns a fresh CLI, actor, Python namespace, product session, output folder and raster ledger reservation. The product, public tool semantics and accepted execution loop remain pinned.

## Accepted code and source bindings

The launcher loads the original localization launcher from its pinned source path. Its accepted `connect` function supplies the real route, consumer, unified result archive, matcher, CLI settings and retained-handle cleanup code objects. A private route globals dictionary selects this namespace, the slot's prompt and the new bridge/bootstrap paths. The accepted batch function is never called.

The accepted consumable-observation freeze supplies the inherited source closure. The new freeze adds this namespace's source, two complete prompts, common input manifest, scoring contract and the unchanged candidate product binding. Product source SHA remains `6d4f7d363aaa48081eff7db467fff20665419172560f19b3a4ccb0fbb46c900f`, installed at `D:/he_consume_001/product`. Repository and installation source bytes remain pinned. Preparation starts zero models and zero rasters.

The input contract uses `inputs.prompts.N` and `inputs.prompts.P`, together with `expected_prompt_sha256.N` and `.P`. Each exact prefix is followed by two LF bytes and the common frozen suffix. Both full prompts and their components are checked before any slot. The only prompt difference is the registered first-entry sentence. The shared CLI retains the existing requested model, effort, tier, tools and isolation settings.

## Common slot timing

Both groups call the same slot wrapper. Its first clock occurs before per-slot source checks, input checks, connection construction and pointer validation. The wrapper calls the accepted route once, including its absolute 450-second deadline, consumer, original process cleanup, archive and route publication. It then performs the same source and pointer readback and closes an independent `SLOT_RESULT.json`.

The end clock is sampled immediately after that slot-result file has closed. `SLOT_TIMING.json` records the two raw timestamps and their difference. Publishing the timing receipt itself is outside that interval. Entry-proof and timing receipts live under `formal/slot_records/<slot>/`, while the unchanged route owns `formal/<slot>/`. A separate batch clock covers shared preparation, all serial slots and aggregate publication. The external parent receipt supplies interpreter startup and full process termination. No aggregate is divided by six and no nested stages are summed into the slot total.

## Limits and terminal outcomes

All six slots retain 450 seconds, 12 business admissions and six charged raster attempts. The shared manifest allows 36 formal rasters and zero preparation rasters. The inherited ledger container retains 44, with the formal and per-slot limits enforcing this batch's executable allowance.

A returned failed route keeps its actual error, final and cleanup records. Ordinary quality failure or recovered business errors do not remove a slot. Batch scheduling separately checks concrete common-interface faults, input identity, actor/CLI retained-handle cleanup, actual thin binding and held terminal status. The original route's validity, safe-to-continue and stop flags remain unchanged in its record. A closed ordinary task failure can continue to the next fresh slot. A missing thin EXIT receipt is retained as unknown when the accepted held-handle contract proves termination. Source or pointer failure, genuine service unavailability, unknown actual process state and launcher publication failure stop later routes. Every unstarted slot remains in the fixed six-row aggregate with `not_run` and its cause. There is no retry, warmup or replacement session.

The final aggregate and launch/timing receipts are attempted through `finally`, preserving route and terminal exceptions. Actual retained function and code-object references establish entry identity, together with frozen source bytes. Connect-time snapshots are labelled separately. Runtime serialization fingerprints are absent.

The root freezes sources and scoring, records the preparation Git, and starts the only formal batch. Quality and adoption are scored before cost analysis. This launcher produces raw timing boundaries and outcomes and makes no quality or benefit decision.

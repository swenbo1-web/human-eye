## 判定

固定工程规划的成本门通过。20 个原配对、40 个运行的整数时界、交错次序、输出 SHA、完整语义 SHA 和工作量记录均自洽，全部配对中优化实现更快。未发现删样、补跑或将冷准备成本冒充零的账本错误。

这里证明的是**预先准备六张全场图后的规划算法优化**。实际生成图数为六张，规划选出两张并核验本地 PNG；尚未验证只生成两张的在线观察闭环，也没有模型端接收、理解与整个任务成本的实测。

## 完整成本边界

`run_benchmark.py` 的每次计时从 fresh JSON 解码之前，到最终结果编码、字节计数和 SHA 之后，包含 ROI 发现、索引构建、六方向连续几何评估、36 个已有图像的像素 helper、选择/停止、两次 PNG 回执核验。共同 import、输入读验、已有数组装载不在每次窗口内；核完整性和逐次进度输出也在计时外，另有整批跨度保留它们。

| 分段 | 原记录复算 |
| --- | ---: |
| 既有六图准备、光栅、编码和逐图元数据发布 | 0.8325849 s |
| 正式批共同 setup | 0.5046185 s |
| 40 次规划计时合计 | 29.2193615 s |
| 整批内其余核完整性、I/O、分析等余量 | 2.2153959 s |
| 正式批开始至分析结束 | 31.9393759 s |
| 两段已记录窗口算术相加（六图准备＋正式批） | 32.7719608 s |

各间隙按原 `start/end` 逐项切分后严格等于余量，没有将跨运行 I/O 全分配给某个 variant，也没有减掉它来救门。六个 PNG 为15735 B，压缩数组为136752 B；本审独立读取 NPZ 的 NPY 头，核对 RGB uint8、depth float64、owners int32 的形状与字节，六图真实载荷23592960 B。

作者逐图字段 `render_and_publish_elapsed_ns` 实际在数组保存和 foreground 计算之后、PNG/数组摘要读取与逐图 metadata 保存之前截止。字段名比实际子窗口略宽；总六图 `total_elapsed_ns` 覆盖后面的逐图 SHA 与 metadata 发布，因此正式总成本没有因该名称漏计。这是读表时的边界说明，不改变作者总成本门。

作为**预算算术示例而非新实测**：若每个 arm 首次使用都完整负担这两项已记录共同成本（832.5849＋504.6185 ms），再加各自规划中位，则参考为2720.533650 ms，优化为1454.475400 ms，组合下降约46.54%，不是91.52%。该组合并非新跑的一次冷任务，也不包含所有启动、最终发布和每次完整性 I/O，不能宣布实际端到端提升46.54%。它仅说明规划变快后，共同准备已成为不可忽略的成本。

六张图的子窗口、最终数组、逐图 metadata 与相机原件逐一吻合。`new_planning_raster_calls=0` 不是零图片费用，而是正式规划复用已支付的六张图。两个被选画面的 PNG 文件验证属于本地交付；本批不支持推断大模型只看两图就会正确答题。

## 固定来源

`FROZEN_RUNTIME.json` 的166路径均读取并计算 SHA，与冻结值、正式 RESULTS 的来源映射、开始标记和 PREPARATION 的 freeze SHA 一致；其中138个是安装产品源码。根另核作者79份交付原件的 Git/最终内容清单，本分工没有重复那套检查。Python 可执行文件也与根级 runtime 中登记的 SHA 一致。

166 是列出的源/输入文件范围，不能说成整个解释器/第三方库二进制封存：NumPy/Pillow只登记版本，没有包含库二进制哈希。当前文件一致本身也不独立证明历史执行字节码身份。这里支持同一个已记录进程下、共享依赖的配对工程比较，不将它扩写成完整运行身份安全验收。

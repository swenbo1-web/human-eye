## 二、三大核心问题深度归因分析

### 问题一：少一次补查，会不会被更大的回包抵消？

**核心结论**：
- **当真正省掉一整轮工具往返时（2 轮 vs 3 轮），更大的单次回包绝对不会抵消轮次节省的 Token 收益**——省一轮带来的全上下文免重放收益（单格省 `~11,500–13,700` Token）是单次几何回包增量（`+5,146 B`）的数倍；
- **本轮净收益被抵消的真正原因有两个**：一是对 `P` 有一格（`sgc03`）因补读**集合外参照物**仍走了 3 轮且首轮打了缩进大 JSON，吞掉了另外两格一半的领先优势；二是对 `N` **根本没有减少调用轮次（同为 7 次：两格 2 轮 + 一格 3 轮）**，在同轮次基准上净背负了更大的工具目录（Schema）与单次响应载荷。

#### 1. 严格区分“可证实的线缆构成”与“不可硬拆的模型 Token 归因”
原始记录仅有整轮 `turn.completed` 的单条汇总 `usage`，没有按系统提示词、初图、工具 Schema、每次工具响应分段的 provider usage。因此**不能声称多出的 `9,328` Token 中具体多少个来自 Schema、多少个来自顶点数组**。但结合单格轨迹与线缆字节，可以确认以下确凿事实：

1. **多轮上下文重放（Context Replay）是总 Token 的第一主导变量**：
   - 九格的总 Token 几乎严格按“**工具调用轮数**”断层聚类：
     - **所有 2 轮调用格**（无论 N 还是 G）：`sgc08(N)=41,969`、`sgc07(G)=42,189`、`sgc01(N)=42,461`、`sgc05(G)=44,351`——全部落在 **`4.20 万 ~ 4.44 万`** 窄带内！
     - **所有 3 轮调用格**：`sgc09(P)=55,674`、`sgc02(P)=55,877`、`sgc04(P)=56,086`、`sgc06(N)=63,512`、`sgc03(G)=70,730`——全部跳升至 **`5.57 万 ~ 7.07 万`**！
   - 原因很直接：每次模型发起新工具调用，服务端都要将 `Prompt + 1.18MB 初图 + tools/list Schema + 历史消息` 重新作为下一轮请求的前缀输入。**多 1 轮调用就至少多背负 `~1.3 万–2.6 万` 的重放 `input_tokens`**。
   - 在同样走 2 轮且首轮紧凑打印的公平对比中，`sgc07 (G, 42,189)` 与 `sgc01 (N, 42,461)`、`sgc08 (N, 41,969)` 的总 Token 差异仅在 **$\pm 0.5\%$（约 220 Token）以内**。这直接证明：只要轮次拉平为 2 轮且首轮不乱打缩进 JSON，同次几何回包本身在低模场景下造成的净膨胀非常有限。

2. **为什么 `G` 的可见字节比 `N` 膨胀了 `+49.52%`（且带工具目录合计多出 `+27,576 B`）？**
   拆解可见字节账本，`G` 相比 `N` 存在三处结构性体积溢价：
   - **第一处：工具目录（`tools/list`）固定底噪（三格共 `+8,028 B`）**：`N` 仅暴露单个 `execute_blender_code`（`575 B`/格），`P` 暴露双插件工具（`2,688 B`/格），`G` 新增 `geometry` 参数与适用域 Schema 后升至 `3,251 B`/格（是原生的 **5.65 倍**）。而且工具 Schema 位于上下文前部，每轮模型请求都要重复计入 `input_tokens`。
   - **第二处：`human_eye_spatial_relations` 单次响应的固定元数据与三角化展开（单格 `12,067 B` vs `P` 的 `6,921 B`）**：
     - 即使在 `P` 组不含局部几何时，单次三对关系响应已达 **`6,921 B`**，其中包含大量对模型解题并无增量帮助但每次必发的审计/契约包装字段（`runtime_source_sha256`、`scene_fingerprint`、`scene_revision`、`document_epoch`、长段英文 `certificate_scope` 免责说明、逐对嵌套证书结构等）；
     - `G` 在此基础上追加 4 个对象的 `56` 个世界浮点顶点与 **`100` 个三角面索引**（将六面体的 6 个四边面拆成了 12 个三角面三元组，并附带 `geometry_contract` 字符串），单次再增 **`+5,146 B`**（三格共 `36,201 B`）。反观原生 `N`（`sgc01`/`sgc08`），第 2 轮一次性打印 **7 个对象**（含参照物 `N12/N04/N19`）的顶点、原始四边面 `polygons` 加上中心距离结果，整个 stdout 才 `8,346 ~ 8,565 B`！
   - **第三处：`sgc03 (G/1)` 的单格异常放大效应（单格比 `sgc07` 多耗 `28,541` Token、`11,583 B` 响应）**：
     - `sgc03` 第 1 轮原生脚本使用了 `json.dumps(..., indent=1)` 多行缩进格式打印 28 个对象，单次响应飙升至 `10,919 B`（而 `sgc07` 单行打印仅 `2,637 B`）；
     - 第 2 轮 `sgc03` 又收下了 `12,067 B` 的插件几何回包；
     - 第 3 轮 `sgc03` 为核实集合外的导轨/双管参照物（`N24/N12/N04/N19`）再发第 3 次调用，导致前两轮累计的 **`22,986 B` 大体积历史工具回包在最后一轮被完整重放了一遍**！这就是 `sgc03` 单格冲上 `70,730` Token、一举拉垮 `G` 组三格总和的直接算术机制。

3. **隐藏的缓存结构警示（`uncached_input` 反升）**：
   尽管 `G` 的总 `input_tokens` 比 `P` 少了 `10,860`，但 `P` 的 `cached_input` 高达 `114,944`（3 轮稳定前缀复用），而 `G` 的未缓存输入（`input - cached = 68,410`）反而比 `P`（`48,678`）高出 **`+40.54%`**、比 `N`（`53,407`）高出 **`+28.09%`**。由于工具回包总是追加在对话末尾（无法命中历史前缀缓存），过大的工具响应直接转化为最昂贵的未缓存输入 Token。

### 问题二：我们提供的能力，是否超过了原生在这道题上的捷径？

**核心结论：是的。在这道题上，插件输出的是“面向任意复杂拓扑的通用严密几何认证”，而题目本身的几何退化特性允许原生走“低模轴对齐区间解析捷径”——插件能力在此题上属于结构性过剩（Overkill），尚未触及原生真正会失败或高成本的场景。**

从 `SEMANTIC_CONTRACT.json` 与九格实际执行代码对照，这道题存在三个使原生极为占优的特征：

1. **几何退化性：世界坐标轴对齐的正交棱柱组合（Axis-Aligned Orthogonal Prisms）**
   - 核心目标 `N16`（带矩形通孔的轴向框，16 顶点）及三个邻件 `N13`（竖直窄隔片，8 顶点）、`N08`（左侧短定位块，8 顶点）、`N28`（穿孔直探杆，24 顶点）的边界面与开孔边界（`X ∈ [0.135, 0.225]`, `Z ∈ [0.325, 0.395]`）全部与世界坐标轴正交或规则对齐。
   - 在正交盒块组合上，判断“实体内部重叠”、“孔洞无碰撞穿过”和“平行平面间隙”，根本不需要 BVH 树、不需要精确二进有理数三角对求交：原生只需打印这几十个世界顶点坐标，观察 `X/Y/Z` 区间落点即可写出**数学上同样完备的解析证明**（如直接指出右框材与 `N13` 的三维开区间交集包含内点 `(0.245, 0.100, 0.360)`，`N28` 截面完全落在通孔开区间内且边界差为 `23 mm`，`N08` 平行面间距约 `0.100009 mm <= 0.25 mm`）。评分合同明确认可合法解析捷径，因此原生在质量上天然拿满 `3/3`。

2. **规模极小性：4 个对象合计仅 56 个顶点**
   - 当选中对象只有 56 个顶点时，“在原生 Python 里直接 `print(verts)` 让大模型肉眼读坐标”不仅完全可行，而且极其简短；
   - 一旦真实工业/角色场景的选中部件包含 **2,000 ~ 20,000 个顶点**且带有**任意欧拉旋转、斜交倒角、非凸凹槽或曲面啮合**：
     - 原生既**不能**把几万个顶点直接 `print` 到上下文里（直接撑爆几万 Token 且模型无法心算旋转平面方程）；
     - 模型现场手写通用三维三角面最近距离 / 闭合体内外判定脚本又极易出 Bug（如此前复杂盲测中出现过的边面相交漏判或耗时数十秒的纯 Python 双重循环）；
     - 同时，**候选 `G` 当前“把选中对象全部 `vertices_world` 和 `triangles` 裸数组原样塞进 JSON”的做法在高模下同样不可持续**（5,000 顶点 + 10,000 三角面会产生 `>350 KB` JSON，直接打穿单次响应预算）。

3. **工作流割裂性：首轮发现与集合外参照仍依赖原生，导致插件路线变成“双轨混跑”**
   - 九格全部 9 次运行中，**第 1 轮工具调用 100% 是原生 `execute_blender_code` 遍历 28 个网格算范围与中心**。
   - 原生路线 `N`（如 `sgc01`）在第 1 轮扫全场时顺手将全场世界顶点字典 `verts` 驻留在 Blender Python 内存变量中，第 2 轮一个脚本同时取出目标 4 件 + 参照物 3 件（导轨/双管）并算完距离，**单工具链闭环完成**。
   - 插件路线 `G` 则是第 1 轮调原生扫目录 → 第 2 轮切到插件查 `N16 + 3 候选`（受限于四对象关系集合上限，未能顺带覆盖判断目标三条件所需的导轨 `N12/N24` 和双管 `N04/N19` 局部细节）→ 若模型严谨起见想再核对参照物形状（如 `sgc03`），就不得不第 3 轮再切回原生！这种跨工具切换使 `G` 在工具轮次上至多追平 `N`（2 轮），一旦多核对一次参照物就输给 `N` 一轮。

### 问题三：下一步是否还应该追求内核毫秒级提速？

**核心结论：在当前任务与资产规模下，应当完全停止对几何微内核毫秒级提速的投入。算术上限（0.31%）已证明内核耗时不是当前端到端成本的控制变量；但剩余的 99.69% 也绝不能笼统归结为“纯模型推理”，其中包含可观的生命周期管道开销、多轮上下文往返开销与回包消化开销。**

#### 1. 算术天花板封死微内核收益
- `G` 组三格完整单格总墙钟为 **`201.186 s`**，而三格共计 7 次宿主工具执行（含原生代码执行 + 插件选择性网格采集 + 精确关系求解 + 局部几何组装）的 `tool_owner_elapsed_ns` 总和仅为 **`0.6188 s`（占比 `0.308%`）**，其中插件 `human_eye_spatial_relations` 单次仅耗时 **`124.7 ~ 128.0 ms`**。
- 即使投入大量研发把这 `125 ms` 优化到 **0.000 ms（无穷倍加速）**，在其余环节不变时，`G` 单格中位数也只会从 `67.174 s` 变为 **`~67.049 s`（仅快 `0.19%`）**，对跨越 10% 门槛和降低 Token 贡献为零。

#### 2. 剩余 99.69% 墙钟的真实去向（严禁全部归为“模型推理”）
从 1.2 节逐格计时拆解可见，除掉 `0.31%` 的工具内核执行后，`G` 组每格约 `64 ~ 70 秒` 实际分布在四个性质截然不同的桶里：

| 时间分桶（`G` 组三格实测范围） | 单格耗时 | 占完整单格比 | 真实物理构成（非纯推理因素拆解） |
|---|---:|---:|---|
| **① 启动与关闭收敛生命周期开销**<br>(`pre_setup` + `final_to_cleanup` + `post_close`) | **7.82 ~ 9.30 s** | **12.1% – 13.4%** | 包含会话前置检查、产品/桥接子进程启动（`G`/`P` 的 `pre_setup` `~1.6s` 比 `N` 的 `~1.0s` 固定慢约 `0.6s`），以及**模型已输出最终答案后等待进程/reader/owner 清理退出的 `5.92 ~ 7.40 s`（`final_to_cleanup`）**！这段时间模型早已答完题，纯粹是运行器与 MCP 管道收尾墙钟。 |
| **② 首轮发现规划窗口**<br>(`prompt_submitted → tool_1_started`) | **12.79 ~ 19.38 s** | **18.4% – 28.9%** | 包含 1.18MB 初始图与工具目录上传编码、服务端排队调度、首轮视觉/空间审题以及生成第 1 段探索请求。 |
| **③ 工具间多轮调度往返**<br>(`inter_tool` 间隔总和) | 2 轮格：**6.52 ~ 8.01 s**<br>3 轮格：**19.17 s** (`sgc03`) | **10.1% – 27.5%** | **最具弹性的优化区**：每增加 1 次工具往返（如 `sgc03` 从 2 轮变 3 轮，或 `P` 组固定 3 轮的 `20.2 ~ 26.2 s`），就多出 **`~11–13 秒`** 的网络传输、API 队列等待、历史上下文重预处理与工具调用生成时间。 |
| **④ 末次工具返回 → 最终答案生成完成**<br>(`last_tool_to_final`) | **27.94 ~ 32.13 s** | **40.2% – 49.9%** | 全场单段最长耗时（`N/P/G` 中位分别为 `29.77s / 27.63s / 31.48s`）。包含：大回包文本读取消化、模型隐式推理验算（`reasoning_output`）以及逐字流式生成约 `1,400–1,690` Token 的严密证明长文（按常规生成吞吐，仅文本解码输出本身就占去十余秒）及客户端事件传输。 |

> **关键发现**：为什么 `G` 在总调用次数与 `N` 相同（均为 7 次）时，完整耗时中位数仍比 `N` 快了 `8.773 秒`（`-11.55%`）？
> 对比 2 轮格（`sgc05/07` vs `sgc01/08`）：`N` 在第 1 轮拿到目录后，第 2 轮需要模型自己构思并手写一段更长的多对象几何提取与中心距离计算 Python 代码（`inter_tool` 耗时 `17.1 ~ 17.8 s`）；而 `G` 在第 1 轮拿到目录后，第 2 轮只需发一个结构化 JSON 请求调 `human_eye_spatial_relations`（`inter_tool` 骤降至 **`6.5 ~ 8.0 s`**，立省约 `10 秒` 代码构思与生成时间）！但到了第 4 阶段（`last_tool_to_final`），`G` 因为要阅读消化 `12 KB` 的展开三角面与证书 JSON，中位耗时（`31.48 s`）反而比 `N`（`29.77 s`）和 `P`（`27.63 s`）略慢了 `1.7 ~ 3.9 秒`，回吐了一部分时间优势。

## 三、方法论复审：严守证据边界与不做的事

结合仓库既有独立复核准则（及最新 `M2-TIGHT-DIRECTORY-001` 工程复核现状），本轮复审明确划定以下红线：

1. **不在原合成题上重刷样本、改字段或降门槛**：
   - 本轮 $n=3$ 已完成一次性筛选使命：证实了“同次几何自然消费成立、同域补查归零”，也证实了“在 56 顶点正交规则场景上，插件无轮次净胜且存在 Schema/载荷体积劣势”。继续在同一道正交题上抠几百字节文案或补跑样本寻找偶然过线，没有真实工程意义。
2. **不把未知项写成零或因果定论**：
   - 未暴露分段 Token 账单，不硬拆 `9,328` Token 差值的精确百分比；
   - 九格薄客户端桥接缺少独立 `EXIT.json` 回执（`confirmed=null`），保持 `unknown` 原状记录；
   - `M2` 紧致目录（`mode="directory"`）目前仅证明了对旧插件 `overview` 冷工具耗时 `-62.86%`、冷响应字节 `-97.91%`，但其完整纯目录会话（`2.497 s`）与冷桥接字节仍高于合理原生脚本（`1.541 s`），且尚未经过大模型消费验证，不能提前计入模型端净收益。
3. **不靠微内核调优或提前上 Hook 掩盖观察载荷本身的性价比问题**：
   - 在单次观察交付的信息密度与任务匹配度未跨过净收益线之前，加 Hook 预载只会把成本转移到前置阶段，无法证明空间观察接口自身的净价值。

## 四、后续高价值研究方向建议（按预期端到端净收益排序）

既然“内核毫秒级速度”与“模型不信任插件”均已被证伪排除，后续研发应完全围绕 **“选对插件真正具备不可替代性的空间任务 + 降低跨工具轮次 + 提高单位字节的几何信息密度”** 三个核心问题展开：

### 1. 任务基准转向“原生简短解析捷径失效”的真实复杂几何（立项前提）
在立项下一轮消费对比前，必须先引入一个未参与调参、且**原生无法靠“打印几十个轴向顶点做加减法”轻松过关**的独立三维任务：
- **典型高价值特征**：非轴对齐（任意旋转姿态）装配体、含几百至数千面的凹槽/曲面/斜孔配合件、外包 AABB 紧邻排序与真实表面间隙排序颠倒（假近邻干扰）、或浅层局部穿插（难以靠肉眼看初图或包围盒区间判定）。
- **预期分化机制**：在这类场景下，原生路线若打印全量顶点会直接爆 Token，若现场手写三维点面/边面精确距离 Python 脚本则会显著增加生成耗时、轮次重试甚至出现几何漏判（质量扣分）；此时插件“一步给出精确关系 + 紧凑局部证据”才能体现真正的解题门槛优势与完整任务净收益。

### 2. 重构局部几何交付形态：从“全量三角面裸数组转储”升级为“按需紧凑几何特征 / 原生多边形”（控 Token 核心）
解决问题一中“回包膨胀 +49.5%、高模不可扩展、未缓存 Input 飙升”的关键，不是删掉局部几何，而是改变交付粒度：
- **避免无差别展开全部 `triangles` 三元组**：在低模需要精确拓扑时，优先交付原始多边形面或紧凑轴/截面范围摘要；在中高模场景下，**严禁默认返回全网格顶点与全三角面数组**，改为仅返回**围绕最近见证点 / 交叉区域的局部特征子集（Local Patch / Witness Neighborhood + 对象紧致包围范围与开孔/实体截面摘要）**，将单次几何增量稳定控制在 `1~2 KB` 量级，使其不随资产总面数线性爆炸。
- **剥离每次调用重复发送的静态契约长文与冗余内部哈希**：将 `certificate_scope` 等静态长段英文解释及对模型推理无用的多重内部摘要从高频工具文本回包中精简或移至会话级元数据，并精简 `tools/list` Schema 描述体积（缩小与原生 `575 B` 的固定目录税差距）。

### 3. 打通“发现 → 参照检查 → 局部关系”同链路闭环，消除首轮与尾轮跨工具往返（控时间与重放核心）
九格数据已清晰表明：**少 1 轮调用 = 立省 `~8–13 秒` 往返时间 + 立省 `~1.1–1.5 万` 上下文重放 Token**。
- 当前插件路线之所以还要走 2~3 轮，是因为第 1 轮目录发现和第 3 轮集合外参照物（如 `sgc03` 查导轨/双管）仍需退回原生工具。
- 后续在整合已通过工程复核的 `M2` 紧致目录与选定观察接口时，应评估让单次选定观察允许附带读取少量**仅需紧致范围/轴心的参照对象（Reference Bounds Only，不跑昂贵的两两关系求解）**——这样模型在 `sgc03` 这类需要核对外部基准物位置的任务中无需再发第 3 轮原生脚本，把 3 轮彻底压实为稳定的 2 轮（并在观察链本身净收益打正后，再通过同服务 Hook 尝试将首轮目录发现进一步压至 1 轮）。

### 4. 工程管道收尾与计量隔离（非推理耗时治理）
- 针对九格中暴露出的 **`final_to_cleanup` 占去 `4~10 秒`（模型答完题后等待进程与管道清理）** 以及插件启动前置多耗 `~0.6 秒` 的现象，后续在评估产品真实交互体验时，建议同时报告 **`prompt_to_final`（用户感知首尾回答耗时）** 与 **`full_cell`（含完整进程生命周期关闭耗时）** 双口径，并排查产品 MCP launcher / stdio reader 关闭阶段是否存在不必要的阻塞等待，避免管道收尾延迟掩盖真实的交互提速。

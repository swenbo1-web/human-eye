## 3. `final_to_cleanup` 到底测到了什么

`consumer_transport.py:226–228` 在收到最后一个公开agent_message完成事件时记 `final_received_ns`；214–219另记 `turn.completed` 及usage。180–230继续等stdout/stderr读完，随后 `process.wait()` 并记 `process_exit_ns`。241–264才做timer/reader回收、bridge退出回执检查、图像文件核对并记cleanup。

因此 `process_exit_ns` 是运行器观察到退出时的记录，不是底层操作系统实际退出瞬间；reader EOF之前的内部情况未分段暴露。以下分解可由已存时间戳精确得到，单位秒：

| 格 | final→turn.completed | turn.completed→观察退出 | 观察退出→cleanup |
|---|---:|---:|---:|
| sgc01 N | 0.001897 | 10.369035 | 0.006691 |
| sgc02 P | 0.001781 | 8.445189 | 0.007323 |
| sgc03 G | 0.516481 | 6.880242 | 0.006977 |
| sgc04 P | 0.001747 | 5.065474 | 0.009329 |
| sgc05 G | 0.001739 | 6.097792 | 0.007651 |
| sgc06 N | 0.001395 | 7.641904 | 0.007347 |
| sgc07 G | 0.001711 | 5.914050 | 0.006888 |
| sgc08 N | 0.001661 | 3.854301 | 0.007007 |
| sgc09 P | 0.001644 | 5.019094 | 0.006957 |

可确认：多数尾部发生在turn完成之后、运行器观察到CLI退出之前；记录中显式退出后的清理仅约7–9毫秒。不可确认：具体是CLI内部等待、某条输出流、连接关闭或其他组件耗时，更不能把它全归给产品launcher或owner。

**owner/product的最终关闭不在这段里。** `driver.py:203–214` 先等待 `consume()` 返回，再调用 `finish()` 通知owner关闭并等待。它属于另列的 `post_consumer_close`（约0.2–0.3秒），不是5.9–7.4秒的G final_to_cleanup。薄客户端EXIT回执仍unknown，不应凭推测补成功记录。

稿件建议并列报告prompt_to_final和full_cell是合理的，而且原件已可计算：

| 组 | prompt→final中位 | full_cell中位 |
|---|---:|---:|
| N | 66.948613 s | 75.946980 s |
| P | 66.676671 s | 73.746320 s |
| G | 59.102507 s | 67.173966 s |

保留两种口径有助于解释体验与资源生命周期，但不能事后用前者替换本轮已经冻结的完整门槛，也不能直接据此派“优化产品launcher收尾”的任务。

## 4. 对后续方案的影响

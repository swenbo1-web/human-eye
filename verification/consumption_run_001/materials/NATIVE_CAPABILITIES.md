The worker creates a persistent namespace containing the actual `bpy` module and executes supplied Python code unchanged through `exec(compile(code, call_SCRIPT_path, 'exec'), namespace)` (source lines230,260). Full Python imports, mathematics, evaluated geometry reads, tool-side aggregation, self-written scripts and variables/caches across calls within that one answer remain available. There is no supplied object inventory, task-specific solver, nearest answer or sample algorithm. The MCP bridge must forward code and the original response rather than adding solutions or lifting the native route into a mesh-dump requirement.

An owned session starts one private asset copy with `--factory-startup --disable-autoexec --background`, checks the expected asset SHA, and binds READY to an owned loopback endpoint, original deadline, PID and helper SHA (lines301–342). Each answer should start a fresh session. The original asset is never saved. `max_calls` is an execute_code sequence limit; close is handled before that limit (lines248–249), so an approved setting of8 permits8 execute_code attempts plus one close. Logical MCP actions and actual physical requests are separate quantities: a production HE action can internally cause more than one physical request. A controller/bridge must meter those independently instead of assuming eight actions means eight socket requests.

Native fixed ceilings are256KiB code,8MiB captured stdout per call and20MiB wire response, with a maximum original session window of600 seconds. The trial's180-second answer limit, eight model-visible actions,1MiB actual public text and lower call ceiling must be enforced by the harness; these limits are not implied by this helper. A parent source that is already using its600-second deadline cannot be extended by later calls. `run` applies an earlier transport timeout and preserves failure/unknown outcomes without replay (lines376–391).

The worker checks initial geometry/material/object identity and source/protected-file hashes before and after each code execution. Scene writes contrary to the task can fail that terminal check and poison the session. This is not a Python or filesystem security sandbox: it does not observe all transient modifications or every arbitrary file/network read. `close` supplies an explicit response and the launcher owner waits/reaps; `WORKER_CLOSED.json` retains initial/final fingerprints and poison state. The close audit event may retain its original unknown label, so event status alone is not closure evidence.

There is image construction/accounting support, not a turnkey camera/view or model image-delivery API. The worker redirects render output to the owned `renders/default.png`, attaches render_pre/post/cancel audit callbacks and scans new PNG files after execution (lines193–215). Native Python can use bpy rendering or other existing tools; no new renderer should be built for this trial. `ImageLedger` validates/decode-qualifies PNG bytes and separates registration, reservation and a coordinator-supplied delivery receipt (lines89–145). It explicitly cannot attest that the model received an image. Arbitrary code stdout still travels inside the original JSON text response (lines261–275), not as an MCP native image block.

The helper's ImageLedger maxima (8images, max_single1024²pixels, max_total4×768²pixels) are not the trial's suggested one-image≤768² freeze. If a common existing Codex image-view function is registered for both arms, its actual file access and model-visible delivery can be recorded within the same answer budget. Otherwise propose an explicit numerical/text diagnostic downgrade for root review. Do not silently infer either a visual win or that full bpy is incapable of making images.

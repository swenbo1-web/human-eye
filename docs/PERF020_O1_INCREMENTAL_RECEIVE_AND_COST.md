# PERF-020-O1 增量接收算法与完整入口验收

## 本批判定

候选 C 消除了每次 TCP 分块到达后对历史前缀的重复 UTF-8 解码和 JSON 解析。正式对照完成一次五组交错序列，30 次运行、300 次观察全部通过输出和来源核验。大档四类完整调用耗时改善 28.85%–29.91%，均为五组达标。

整版性能准入为失败，12 个类别通过 8 个。小档姿态中位数和几何 p95 超过回退预算，中档首次与几何类别改善及组数不足。按预注册规则，以提交 `f1ebd7d2d9ca4e58cfa1d40996a49e75807c8892` 恢复已验收 A 源码。候选提交、wheel、隔离安装和全部证据保留，交主复核决定后续。

本批完成了一轮实质接收算法优化和批内独立审核。PERF-020 的驻留、增量传输及模型任务消费仍有后续工作。

## 实际消失的工作

接收循环对每个新 chunk 扫描一次，用两个标准库 bytes 正则及少量跨块状态识别外层对象可能结束的位置。字符串中的括号、转义符和跨块转义单独处理。完整后，原严格解析器对当前全部缓冲区执行一次解码和解析，同一块内的尾随内容也进入严格解析。内部信封保留原有独立解析。

改动为 52 行增加、14 行删除，跨块状态包括起始标记、字符串、待完成转义和容器深度。消息语法仍由已有严格加载器决定。有效响应保持完整值，非法非对象根及确定非法输入可以更早拒绝。实际调用仍为一条请求、一次发送、一个连接，保留本次入口配置的 10 秒期限、64 MiB 限额和动作未知结果语义。

三份冻结真实外层响应以 64 KiB 确定性切块，得到下表。累计解码字节计量的是 CPU 输入量。

实际模块外部插桩验证只扫描新块，搜索位置单调，最终外层值及公开采集返回值哈希一致。公开入口的内部信封解析各一次。此回放使用固定切块，实际网络分块可能不同。

作者单独完成的未计分 feed-loop 诊断保留三包各五次全部样本，独立审核复核其绑定和计量范围。墙钟中位数约为 0.515、4.846、23.244 ms，计时包括 Python 循环、结果列表和计时器开销，排除边界对象创建、chunk 分配及解析。CPU 读数呈 15.625 ms 量化，小包的零值无法表示无成本。扫描开销已经包含在正式 C 的完整 RTT 和实际进程 CPU 中。

## 剩余成本和后续判定

本轮消除的是不完整前缀重复解码和解析，接收逻辑仅增加小型边界扫描。更简单的既有替代是继续使用 A，当前已按门限执行。协议具备可信长度或分隔边界时可直接确定完成位置，但这需要上游协议适配。

剩余主要工作包括完整 Blender 场景采集、世界坐标与拓扑构造、约 11 MiB 大档 JSON 的一次编码/解析、完整 RPC，以及外部验证重建。大档原获益不依赖减小点面、缩减任务或降低精度。中小档固定成本占比及小档尾部原因仍需要主复核结合原始阶段判断。

下一项候选应由主复核依据以上结果选择，例如在已证明的接收重复成本上寻找低开销完成策略，或按总计划进入更大的完整传输/驻留成本。先限定一个已证实瓶颈、注册收益边界，再形成新的固定候选。当前批次在回传后等待主复核，模块完成状态继续开放。

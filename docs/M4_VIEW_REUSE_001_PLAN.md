# M4-VIEW-REUSE-001

用户最新要求：处理重复 SCENE 请求导致重复构造的问题，避免后续任务多次重复渲染。本批是这条新要求对应的有限修复，不改变已经完成六槽运行的 M4-ROUTED-TASK-BENEFIT-001，也不重写消费001第三项失败。

## 决策及边界

可做小范围修复。产品 `ActiveObservationImages.render_view` 已缓存帧，服务端也已有来源/代际绑定；缺口在产品帧与后续原生读取之间。现消费适配器登记了产品图片，却没有填入消费者的 `buffers`；其 `render_views` 合同还明确每次 fresh。因此重复请求重新调用了 raster。

同时，产品只有 patch owner，原生接口提供 raw triangle ID。二者不能直接互换。现 raster 的第四缓冲只是随深度获胜像素写入调用者提供的 face ID，不参与深度计算。首次渲染可先保留 raw winner，再用已有映射生成 patch owner，无需改光栅内核、重算像素或增加几何求解。

本批交付范围准确称为“产品帧补齐来源编号，并接通版本化消费入口的帧复用”。不能声称任意 Blender/第三方原生 render 工具都已自动复用，也不新增默认 MCP/Hook 路由或通用缓存系统。

## 最小实现

1. 在产品现有 mapping 建立时准备稳定的全局源三角形编号，由既有 face offsets 定义；首次 raster 将这些编号传入现有第四缓冲。以 `raw >= 0` 的显式掩码查 `face_patch_ids[raw]` 得到原 patch buffer，背景保持 -1。未支持三角形仍保留其 raw ID，但 patch 为 -1。原 object owner、颜色、深度及源面的顺序不变。
2. 产品帧的内存 buffers 与保存/回读路径同时保留 `triangle_ids`、`patch_owners` 及已有映射。不要把三角形数组塞入模型摘要。现有 2/3/4-buffer raster 公共返回合同不变；历史证据不补写。历史帧缺 raw ID 时明确标记该能力缺失，不能把 patch ID 当作原编号。
3. 新批版本化消费适配器注册产品帧时，用同一份数组填入现有消费者 buffers，并保留 by_ref/by_view 与图片来源。随后 `render_views(names, fresh=False)` 默认取已有同版本帧；无有效帧才构造。`fresh=True` 明确请求重新构造。旧冻结适配器仍维持旧 fresh 合同；新入口说明必须与行为同步，不能靠提示模型少调用实现优化。
4. 原生首次构造的帧也进入同一消费端表，故连续重复调用可直接命中。同一次 names 中重复的视图只构造一次；是否重复交付图片沿明确返回规则记录。复用已有场景代际、来源、相机/投影/尺寸、对象顺序、owner schema 和映射绑定，不新建第二套全量哈希流程。场景或相机变化走已有失效路径，不以 view 名称单独判断跨代际相等。按视图名取得最新帧可以保留兼容，但旧 frame/buffer ref 不得随 fresh 被重定向；图像同字节也不能掩盖 owner schema 的变化。旧帧缺所需 raw 能力时记录 capability miss，构造一次完整帧后缓存。
5. 命中返回已有图片、数组和稳定引用，不重复 PNG/NPZ 发布。新增构造数为0，历史构造成本不退还；图片重新附送、编码、公开字节及模型消费按实际发生另计。`cached`、来源、构造次数必须准确。显式 fresh 的构造即使后处理失败也计入原有构造账本。

如果目前公开产品帧回读会丢弃新增数组，应在原回读路径修正；不能仅给测试脚本伪造 buffers。复用方案必须使用真实产品安装返回的帧。首次开销和数据量需要实际测量：512×512 int32 raw buffer 为每帧1 MiB，三帧3 MiB；这只是数组体积，尚不含临时查表、压缩文件或序列化开销。

## 有意义的验收

- 产品观察 SCENE 后，后续原生读取连续请求同一 SCENE 三次：SCENE 单视图总实际 raster 保持1，返回像素及 raw/patch/object owner 正确；完整观察已构造的 BACK/LEFT 等其他帧另计。同时覆盖原生先构造再重复读取，以及同一批 names 重复。
- 不同视图首次请求正常构造；`fresh=True` 恰增加一次实际构造，旧引用仍指向旧帧。相机/投影/尺寸变化、场景代际更新、对象删除或顺序替换、owner schema/映射变化分别验证已有失效机制。没有 stale 命中，消费适配器已有帧命中不额外做全量几何采集/哈希；本批不改 live_service 已有 host capture 流程。
- 同一组源输入比旧版：RGB、depth、object owner、patch owner 逐元素相同，raw winner 与独立直接 raw-ID raster 相同。至少覆盖多对象、一个 patch 含多三角形、unsupported 遮挡、背景、近/远遮挡、等深首个获胜和裁剪后三角扇。不能用反向 patch 查表冒充 raw 的独立答案。
- 保存后重新读取仍具有一致的 raw/patch/offset/object 关系；旧三/四缓冲消费者和历史帧按原兼容范围工作，缺失 raw 时不得宣称存在。
- 缓存命中、显式 fresh、构造完成后发布/交付失败的分段计量正确。重复交付不虚报新增 raster；已经发生的构造不因异常退款；错误后的下一次请求不引用半成品。

相关单元/集成测试与隔离安装各走一次，优先复用现有有意义反例。无需真实用户资产、共享 GUI 或付费模型。原既有支持集、覆盖集、unknown 和 brief-v4 事实保持一致；引用因版本改变正常变化。源码/安装绑定在本新候选上统一核对。

## 成本与停止规则

执行前固定一次小规模配对测量，最多5个配对块，交替旧/新次序；每块同源同相机同尺寸，缓存各自新建。分别记录首次产品帧，以及“首次产品帧 + 同视图三次后续读取”的总成本，保留全部原始样本。不要通过提前计算新数组、预填缓存或只计热命中来隐藏首次代价。

记录实际 raster/PNG/NPZ 次数、首次与重复服务耗时、新增内存/数组与文件字节、重复附图交付开销。先报告首次成本，再报告一次重复后的累计收支及三次重复的累计收支。不从工具节省推导完整模型时间或 token 节省。本批新增模型消费者0；已冻结六槽结果继续使用原版本，不能与本批混算。

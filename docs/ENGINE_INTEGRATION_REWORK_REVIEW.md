## 接口及原生证据

逐对象 `CaptureChange`/代号、禁图与公开 `NONE`、共享 graph 内的 Outcome 顺序、计划撤销、迟到/重复/关闭票据、静态 relative basis 和 before 所有权均可成立。目标回读及实际控制量先完成，再物化 Outcome，随后才采集上下文；已经实测的结果不会因后续 TD、VG 或 AO 失败而丢失。写入前、setter 状态未知、写后尚无实测分别表达，没有自动重试、回滚或备用链。

主干调用已归档 runner，在新的 `preflight_002/root_replay_001` 独立执行六个 stub 故障控制和两个后台 Blender 原生控制，退出码均为 0，输入/源码稳定、实际导入对账无差。六例 stub summary 逐字节一致；原生 10 个 AO/PNG 文件逐字节一致，summary 仅 40 个进程内 bridge/graph 地址不同。stub 属于假宿主故障注入，不能称作 Blender 原生故障测试。

独立 CPU 审查另验证了就地改写借用 world buffer 后联合 AO 的 before 仍等于原公开包；context、TD、render、AO 四处失败都保留同一个真实 BC Outcome 和一次 A 更新资格；同 owner 下错观察/附件/方向均在消费前拒绝。当前 3 项便携测试通过。物理不变的单位重编码、reference-follows、目标拓扑行重排、zero-open/zero-SECTION、部署加载、完整两会话交错与重开等已登记控制仍留在生产阶段，不将它们追认为已完成。

来源审查核对作者 138 个证据文件、八个过程各自 571 项源归档及实际输入/加载回执；清单可逐字节重建。旧/新 15 AO、14 PNG、schema 共 30 文件和八份视觉记录逐字节相同。原严格视觉仍 7/8，随动屏方向负样本和 false 标签保留。原生首轮掩码断言 11 写错、B/B 首轮预热图像不一致及其源/日志均保留。后者随后改为恢复 authored location/rotation_euler/scale 并通过原图像对账；首测未留差异矩阵，不能宣称已独立还原其具体数值因果，也不能把重新分解的 matrix 当作精确通道复位。

原生导入回执实际覆盖退出时已加载的项目文件，并非全部 venv/动态库；launch 记录环境覆盖项，仍继承未完整登记的环境。后续新进程补 Blender/Python 可执行文件摘要、实际 Python/NumPy/Pillow 版本和路径、设备/backend/driver，以及影响线程和设备的白名单环境有效值；不输出无关环境或凭据。保留本次来源声明的边界，不为补运行时指纹重跑已经通过的功能。

## B/B 失败成立，原因尚未证实

独立重算 216 条时序，其中 30 预热、186 正式计量臂次，即 93 对；五个汇总与作者精确一致。

| 段 | 两方向 p95 比的最大值 | 原 ≤1.05 门 |
| --- | ---: | --- |
| 前观察 | 1.01050452 | 通过 |
| 动作 | 1.01538078 | 通过 |
| 反馈 | 1.02493465 | 通过 |
| 下一查询 | **1.07681014** | **失败** |
| 连续整段 | 1.01823437 | 通过 |

下一查询跨三例 p95 为 21.576970/23.234300 ms。主要差异位于 shape 的 `I-open-tip-1`：lane 0/1 的中位为 22.0696/23.9399 ms，局部比 1.084746。31 对中 21 对 lane 1 较慢，配对差中位 +0.9266 ms。其 lane 1 先执行/后执行中位为 22.1646/24.44065 ms，lane 0 为 21.9072/22.0696 ms，存在物理臂与先后次序的交互迹象。另有同一 pair 两臂跨段同时变慢的记录。现有原始数据没有 GC 或调度轨迹，不能指定根因为 GC、GPU、后台负载或单纯噪声。

QPC 的 100 ns 分辨率及空调用约 100 ns 不能解释毫秒级差异。平衡相邻顺序块可得到不同的描述性比值，但不得替换原失败统计。模型初始两环均 240 行、容量 4096，本轮只追加 V 两行/A 至多一行；恢复权重与 writes 后，残留在活动前缀外，现有读取不会见到。本轮未发现活跃模型漏复位，但这不是任意满环状态都能这样恢复的证明。

一个实际证据缺口是：原 B/B 对 before/after 图像、方向和反馈核对充分，**next 仅核对了 plan 的观察 ID**，没有保存其 PNG、访问顺序、完整 ray、模型输入和反馈后活跃模型状态的两臂等价。必须先确认下一查询工作相同。不能直接扩为三 seed×24 例，借不同 p95 排名使这次差异淡出主统计。

## 资源读数的正确含义

当前 Win32/DXGI 探针证明指定进程、适配器/node 的 current 读数可取得，尚未证明热段峰值可测。托管脚本没有在热链前 `reset_peak()`，报告的 7,262,572 B 是从启动 tracing 后的累计峰，包含场景/模型准备，不能称为已经隔离的热峰。close 后 NumPy owner 为零仅对传入的 control/renderer 根成立，不能推断调用者仍持有的 reference、返回包、票据和全部进程资源都已释放。

后续限定的方法探针必须明确保留根及基线：独立列 owner 去重字节与 tracemalloc，热链前记录 current 并 reset_peak，返回 bytes、reference 和票据按相同策略保留/释放；不把 owner 字节再加到已经包含它的 traced current。关闭验证本会话不再拥有资源，允许调用者继续消费旧 bytes，不要求驱动/allocator 立即将工作集归零。

RSS/DXGI 的五个分点不是峰值轨迹。下一次固定 B 探针可验证约 2 ms 的目标采样间隔、实际最大间隔、同进程/适配器归属及字段分辨率；必须保留时间戳、阶段点和 LOCAL/NON_LOCAL 原值。先明确承诺的是“采样可见峰”还是可归因的真实分配峰；有间隙的采样不得声称覆盖间隙内全部短峰。256 KiB/1 MiB 和 RSS/GPU 各 8 MiB 仍是待方法冻结的候选门，没有 I 增量成绩。

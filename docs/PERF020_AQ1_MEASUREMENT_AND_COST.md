## 两项测量修复

### 完成记录

测试器的重复直接写入函数合并到一个 QA 发布助手。记录先完成序列化，在同目录独占临时文件中写完关闭，再通过当前 Windows 环境已验证的原子不覆盖发布生成完成名称。BLENDER_READY、WORKER_PROCESS、SERVICE_READY、固定模板及终态 JSON 使用同一合同。

读端只等待尚未发布的路径。已发布的坏 JSON、错误绑定和超限记录立即失败，诊断绑定那一次实际读取的长度、SHA256、最多 4096 字节原始前缀和异常。期限在读后及校验后继续检查，清理异常单列。

作者完成 22 项发布测试及七个真实 venv 生命周期故障场景，覆盖半写、已有目标、坏完成、同次读取、writer 退出、原期限、两个 reader 线程启动故障和错绑定。新增助手集中在当前 QA 目录，产品算法按固定版本参与对照。

### 实际进程资源

原测试器使用 Popen 句柄，Windows venv 下采到了启动器。主复核确认旧 `service_resources` 和 `client_close.resources` 无法作为真实服务 CPU/RSS，历史逐运行 Popen PID 缺失，实际父子关系无法补还。旧 WORKER 自身请求 CPU 与 caller RTT 保留原范围，旧封存保留原件。

新测试器先绑定启动器 PID/创建时间，由 worker 在产品 bootstrap 前发布实际 PID、创建时间、父 PID、映像和 run binding。控制器持有实际服务句柄后再创建 reader 线程，并将后续 READY、WORKER 及退出采样绑定到同一创建实例。启动器、服务和 Blender 分栏。

三个实际探针各触碰 32 MiB 并执行至少 150 ms 的自身 CPU 工作，证明实际服务与启动器计量有别。READY 前终止启动器后 child 继续存活的反例验证了单独回收实际解释器的必要性。活跃进程退出时间记为 null，退出后内存记为 unknown，存活期峰值保留采样边界。

两 arm 各十次无计分 fixed-entry smoke 全部通过。A 在十次宿主执行前均未加载 array，B 首次未加载、后九次已加载。首次实际产品导入发生在原执行路径内。

## 解决的问题与授权来源

完全访问解决本地读写和命令权限，不能代替插件明确要求的表单。原专用恢复入口每个目标仍要求真实 MCP form；`never` 下不能假设自动勾选。新增模式由受信本机启动命令显式授权一个具体任务，读取、求解、多顶点执行和回读共用一份授权，无需插件逐动作索取表单。

这不是永久 `auto_approve=true`。启动时固定操作者配置、场景/参考/源码摘要及1–8个原顶点，之后绑定新 worker 的完整源、实例、文档、坐标、单位和矩阵。一次调用必须与该集合完全一致，不开放逐次子集续算；整个集合由已有 RestoreController 在 Blender 内执行。当前首版不支持任务中追加目标或追加额度。

入口仍是安装后的 `surface_owned_entry.py`，在既有 `--operator-config` 外显式给出：

```text
--operator-task-root <新的绝对回执目录>
--authorize-indices 6 12
```

以上是操作者启动参数，MCP 模型参数仍只有 `indices`，不能传授权、路径、参考、时间或预算。需要直接本机执行时再加 `--execute-task`，返回同一引擎执行回执。受信本机调用者必须已有这项任务的操作者授权；代码不抵御同账户任意 Python。不能把普通模型提议当作操作者批准。

默认不带这些参数仍走原严格表单路径。destructiveHint 保留，宿主可能另有工具级批准；本模式只消除插件内部逐目标 form，不承诺关闭所有平台审批。未修改 Codex 权限、默认 live、Hook 或已有 MCP 配置，新模式没有静默替换当前聊天的旧两工具连接。

## 期限、回读和故障

原30秒从操作者启动登记起算，包括初始化、只读检查、准入和执行；模型请求、状态读取和重复 ID 都不续期。worker 原窗口不能改成调用到达后重新30秒。每顶点最多1毫米、最多2N次 setter（含恢复）、原三角网格、保护区和每步离散接触检查均复用旧内核。没有连续曲面扫掠保证，没有保存命令。

任务目录采用排他 mkdir；记录接收、源绑定、请求、确切 scope 和最终回读。scope 先持久发布再回复 worker；即使初始文件发布失败，留下的目录也不能重新发行 live 授权。JSON 是历史凭据，构造器从不读取它恢复 grant。一次目标消费后，换请求 ID也不能再写。重启需要新的明确任务，不能自动复制目录或重开旧任务。

最终还做一次独立 worker 读取，核对目标/保护区完整网格、实例/文档及真实物理计数；回执丢失、末次回读不一致或写后发布失败不能转成零动作拒绝。未知状态关闭 worker，原内核 journal 的未知跨重启保留。父进程 EOF 后 worker若已确认未批准并提交终态，可以是已知零；只有实际未完成的记录才标未知，不能把所有崩溃一概填零或一概填未知。

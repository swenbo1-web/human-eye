## 每批怎样推进

1. 复核者根据最新实际失败固定一个 cycle：问题、源码/数据基线、交付、评价和停止点。
2. 实施者核对实际用户授权、自己的 Agent Learning 身份、Git 状态和合同；完成本批实现、可复跑探针及原始结果。同批可恢复错误自行处理，不因一次报错结束。
3. 实施者固定提交，记录成功/失败/未运行项，向复核对话发送一次完成回报后结束该批。已有未回报工作先回报，不重复开同一批。
4. 复核者读取固定提交与原件，检查输入/标签/划分、模型或几何算法、泄漏与完整成本；按需要在隔离位置重放关键探针。明确区分作者结果和自己实际验证。
5. 复核通过后选择一个下一任务；发现缺陷时只返工明确缺口。达到阶段目标或缺少真实必要输入时，给出具体结论，不靠换题或改门槛维持循环。

## 深度复核必须回答的问题

- 输入是否包含决定正确答案的信息？是否把最终求值结果放进了输入？
- 标签表达的是物理量、任务允许的形变，还是实际艺术偏好？不同答案来源不能混同。
- 同资产、同绑定和派生样例是否跨训练/测试？分母以独立资产/任务列明。
- 既有几何或插值方法是否获得同等准备、目标和复用机会？
- 收益来自模型架构、输入表示、更多监督数据还是更多计算？是否把这些因素混在一起？
- 包括采集、准备、构图、特征、全部尝试、求值及反馈后，收益还剩多少？
- 未解决任务属于诊断、候选缺失、排序、修正预测还是执行偏差？下一批是否真正针对它？
- 多类异常共存时是否保留全部相关标签？方案是否来自同一状态，联合目标是否同时满足，改动越过选区或跨帧后的影响是否纳入实际反馈？按 [耦合合同](M6_COUPLED_EXPERT_CONTRACT.md) 单列组合漏检、引入问题、冲突及运行错误，不以单类均分代替。

模型初版后至少实施一次有根据的优化候选并对照；候选没有改善则保留初版。初版与一次优化后必须做去留决定，额外迭代需新失败证据，不能无止境换随机种子、放宽指标或扩模型。

这一轮优化可通过减少重复准备、改进表示或批处理完成，不等于必须再训练一种模型。首选未达标时先定位信息/数据/目标或算法缺口，不自动依次试遍所有架构。

## 完成主动回报

实施者在确认人类授权后使用 `send_message_to_thread` 回报复核对话，消息含：`cycle_id`、状态、固定提交、工作树、报告/原件路径、实际运行项、失败/未运行项、最多两个候选与建议下一步。源消息位置是本复核对话，必须读取实际用户指示，不仅依赖转发文字。

发送回报前写入 `verification/<cycle>/HANDOFF.json`，成功后记录工具回执；回复丢失时先核对发送状态，不盲目重发。发送失败时保留错误及文件，并在本批最终答复中提供同样交付。

复核者只在实施者空闲且交付固定后派下一批；同一 cycle/commit/交付只审核和派发一次。实施者活跃期间不插入重复提醒，也不并发修改其文件。

用户最新明确要求“不用兜底检查”。M6 的 30 分钟 heartbeat 已删除，不再设置定时轮询。实施者完成后主动唤醒复核对话；收到回报或用户指示后，再按需核对状态、固定提交和原始结果，按上述流程复核。

当授权阶段全部完成、用户暂停/替换工作、或仅余无法自行解决的输入/权限/额度问题时，停止派单并说明原因。不能将某一批完成误认为整个 M6 阶段完成，也不能为保持循环而增加模块。
